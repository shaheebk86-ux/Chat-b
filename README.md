# PRIVATE DUO CHAT

A responsive, browser-based real-time chat for exactly two active participants per room. Built with Node.js, Express, Socket.IO, vanilla HTML/CSS/JavaScript, and SQLite.

## Features

- Cryptographically generated 12-character room codes (stored as keyed hashes).
- Server-enforced two-active-participant limit with atomic SQLite transactions.
- Per-participant random bearer session token; only its hash is stored in SQLite.
- Reconnection grace period (90 seconds by default); explicit leave immediately frees a slot.
- Real-time messaging, typing indicators, presence, and bounded message history.
- Client-generated message IDs make retries idempotent and prevent duplicate inserts after an acknowledgement timeout.
- Persistent SQLite messages, WAL mode, foreign keys, indexes, and optional retention.
- Responsive dark/light UI, keyboard support, reduced-motion support, and safe `textContent` message rendering.
- Helmet headers, explicit origin allow-list, HTTP and Socket.IO event rate limits, input limits, and generic errors.

## Requirements and installation

Node.js 20.11 or newer and npm 10+ are recommended.

```bash
unzip PRIVATE-DUO-CHAT.zip
cd PRIVATE-DUO-CHAT
npm install
cp .env.example .env
```

Generate a strong pepper and place it in `.env` (do not commit it):

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Set `ROOM_CODE_PEPPER` to the generated value. For local use set `ALLOWED_ORIGINS=http://localhost:3000`. Then run:

```bash
npm start
```

Open <http://localhost:3000> in two separate browser profiles/devices. Create a room in one and join using its code in the other.

## Environment variables

| Variable | Required | Default | Description |
|---|---:|---|---|
| `NODE_ENV` | no | `development` | Set to `production` for deployment. |
| `PORT` | no | `3000` | HTTP listener port. |
| `ALLOWED_ORIGINS` | recommended | `http://localhost:3000` | Comma-separated exact browser origins. No wildcard is used. |
| `ROOM_CODE_PEPPER` | yes | — | Secret, at least 32 characters, used to HMAC room codes. Keep stable across restarts. |
| `DATABASE_PATH` | no | `./data/private-duo.sqlite` | SQLite file path. |
| `MESSAGE_RETENTION_DAYS` | no | `0` | `0` keeps messages indefinitely; positive integer deletes older messages on periodic cleanup. |
| `DISCONNECT_GRACE_SECONDS` | no | `90` | Time disconnected participants can reconnect before their slot is freed. |

Changing `ROOM_CODE_PEPPER` makes existing room codes unresolvable. Back it up securely.

## How rooms and identity work

Room codes are generated by the server with cryptographic randomness. The database stores an HMAC-SHA-256 hash of each code, not the readable code. A participant receives a random session token; only its SHA-256 hash is stored. The browser keeps the code and token in `sessionStorage` for refresh/reconnect in that tab. A display name is only a label, not verified identity or authentication.

A room has at most two `active` participant records. Join checks and inserts run in a synchronous SQLite transaction, so concurrent joins cannot pass the two-slot check together. An explicit leave marks a participant left immediately. A network disconnect leaves the slot reserved for the grace period; successful resume cancels expiry. After process restart, existing sessions get a fresh grace window. This implementation is intended for one Node.js instance.

## Database and retention

SQLite uses WAL, foreign keys, a busy timeout, and indexes for room membership and message history. The most recent 50 messages load at join; older messages can be requested through the socket history event. Messages remain after a participant leaves. Default retention is indefinite. Set `MESSAGE_RETENTION_DAYS` to a positive number to enable automatic deletion; this policy is applied periodically. Database files are not served from the public directory.

## Security and privacy

- Use HTTPS in production. Socket.IO will use secure WebSocket transport through the HTTPS origin.
- Configure `ALLOWED_ORIGINS` to the exact deployed site origin(s), e.g. `https://chat.example.com`.
- Keep `.env`, the SQLite file, and backups private. Never publish the room-code pepper.
- Helmet supplies security headers and a restrictive content security policy. API and socket event rate limits are applied. User message content is inserted as text, never HTML.
- Room-code possession is the invitation mechanism. There is no account system, verified identity, or multi-factor authentication.
- **This is not end-to-end encrypted.** Browser-to-server traffic should be protected by HTTPS, but the server processes messages and stores message text in SQLite. The server/database operator and anyone with access to those systems may be able to read stored messages. Do not use it for highly sensitive communications without a separate security review and an actual E2EE design.
- Session tokens are bearer credentials. Anyone who obtains a participant's token and room code may be able to resume that participant session. Protect the device and avoid sharing browser storage.
- Single-instance only: active socket coordination and reconnection timers are in process memory. Do not run multiple replicas or workers without shared coordination and a distributed adapter/locking strategy.

## Render deployment

1. Create a new **Web Service** from this repository.
2. Build command: `npm install`.
3. Start command: `npm start`.
4. Set `NODE_ENV=production`, `ROOM_CODE_PEPPER` (strong random value), and `ALLOWED_ORIGINS=https://YOUR-SERVICE.onrender.com` (replace with the actual origin).
5. Add a Render persistent disk and mount it at `/var/data`.
6. Set `DATABASE_PATH=/var/data/private-duo.sqlite`.
7. Set the health check path to `/healthz`.
8. Keep the service at a single instance. Do not enable autoscaling/replicas for this in-memory room manager.
9. Use the Render HTTPS URL; configure any custom domain in `ALLOWED_ORIGINS` too.

The free/ephemeral filesystem is not suitable for persistent SQLite data. The persistent disk is required. Back up the database and pepper together. Render disk availability/pricing and platform settings may change; verify them in the current Render dashboard.

## Troubleshooting

- **Server refuses to start:** confirm `ROOM_CODE_PEPPER` exists and is at least 32 characters.
- **Browser says server unavailable:** confirm the server is running, the URL is correct, and the browser origin is listed exactly in `ALLOWED_ORIGINS`.
- **Room code rejected:** codes are case-insensitive, 12 characters; the creator must share the current code. A code is not a password substitute.
- **Room full after a disconnect:** the slot remains reserved until the reconnect grace period expires. The participant can refresh/reconnect using the same tab session.
- **Messages not persisting on Render:** check that `DATABASE_PATH` points inside the mounted persistent disk.
- **Cannot resume after clearing session storage:** the participant token is gone; rejoin as a new participant if a slot is available.
